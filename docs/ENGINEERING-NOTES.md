# Engineering notes

Measured behaviour, gotchas, and the reasons behind decisions that are not
obvious from the code. Nearly everything here was paid for once already --
by a diagram that came up blank, a poll loop that froze for 82 seconds, or a
settings file that was almost written wrong. Read the relevant section before
changing the relay paths, the RDB writer or the themes.

## What this is

**PAC CT — Protection, Automation & Control Commissioning Toolkit.**

Web toolkit for commissioning protection, automation and control systems —
SEL relays today (SEL-411L, SEL-451, SEL-487E, SEL-751, SEL-787, …), with
IEC 61850 tools that already serve any vendor. Nine tools, six shipping, all
served from a single dashboard on one port.

They are still six shipping and three planned, but the menu now presents them in **four vendor sections** — vendor-neutral, SEL, GE, Siemens — the last two declared and still empty. The six shipping, in menu order:

- **VLAN Mapper** (vendor-neutral) — derive GOOSE VLAN port maps from SCD.
- **Visualizador de Lógica (GLV)** (SEL) — live overlay of relay state on GLE logic diagrams (telnet to relay).
- **Comparador de Ajustes** (SEL) — up to 7 relays of one family side by side, with SELOGIC equivalence rather than text diff.
- **VB Updater** (SEL) — sync Virtual Bit descriptions between GLE and SCD (IEC 61850).
- **Exportador de Comentários GLE** (SEL) — round-trip GLE port comments via Excel.
- **Editor de Mapa DNP** (SEL) — edit each relay's DNP3 points (`SET_D*.TXT`) and re-export the RDB.

Plus **Arquivos do Projeto** (`/files/`), which is not a tool: it is the only screen that accepts an upload, and every tool picks from what it holds.

## Run

Always launch via the entry point — it auto-bootstraps `.venv/` from `requirements.txt`:

```bash
python3 app.py --web                          # default: dashboard on :8765
python3 app.py --web --port 9000 --config other.ini
python3 app.py --web --gle samples/foo.gle.xml
```

CLI mode (`python3 app.py` without `--web`) only drives the GLV terminal poller — rarely used.

Do not manually create venvs or run pip. `app.py` handles it.

Distribution (Phase 5, `src/pacct/update.py` and `tools/build_dist.py`):

```bash
python3 app.py --versao       # what am I running (works on a broken install)
python3 tools/build_dist.py   # dist/pac-ct-<version>.zip + manifest.json
python3 app.py --instalar     # first install of an unzipped bundle
python3 app.py --atualizar    # check GitHub Releases and update
python3 app.py --reverter     # point `current` back one version
```

## Project layout

- `app.py` — venv bootstrap + entry point. Delegates to `pacct.cli.runner` or `pacct.web.dashboard`.
- **Two libraries were extracted from this repository, and most of the file
  handling now lives in them.** Neither knows the web exists:
  - **`selfiles`** (https://github.com/GuilhermeMarini/selfiles) — everything
    that reads an SEL project's files, which used to be `pacct/parsers/`,
    `pacct/core/` and `pacct/matchers/`: `selfiles.rdb`, `.rdb_cache`,
    `.settings` (was `sel_settings`), `.dnp_map` (was `set_dnp`), `.gle`,
    `.dnp_profile`, `.selogic.{parser,compare,model,catalog}`,
    `.models.{relay_models,wordbits}`, `.scl.{read,mms_tables}` (was
    `parsers/scd` and `core/mms_tables`), `.match` (was `matchers/relay_scd`).
    **The three per-model registries ship inside it**; what stays here is an
    OVERLAY at `paths.DATA_DIR`, searched first, per model, and written to by
    "Importar perfil DNP". `pacct/__init__.py` calls `selfiles.configure()`
    once, at import, before any registry can memoise a different answer.
  - **`cfbwrite`** (https://github.com/GuilhermeMarini/cfbwrite) — the
    Compound File writer, was `pacct/parsers/ole_rebuild.py`.
- `pacct/` — the application: the web toolkit, the CLI, and the relay
  conversation. Import as `pacct.<module>`, never relative.
  - `pacct/paths.py` — **always** use these constants for filesystem paths.
    Three roots, and the distinction matters: `PACKAGE_DIR` for what travels
    inside the package (templates, fonts), `PROJECT_ROOT` for the project
    (found by marker, or `PACCT_ROOT`), and `DATA_ROOT` for mutable state --
    `config.ini`, `cache/`, `rdbs/`, the data overlay -- overridable with
    `PACCT_DATA_DIR` so a versioned install can keep the engineer's files
    outside the version being replaced.
  - `pacct/core/` — what talks to a relay: `relay_conn.py` (the one place
    that touches selprotopy's privates) and `target_region.py`. The file
    formats left for `selfiles`; these stayed because they need a relay.
  - `pacct/web/` — dashboard + the tool modules.
  - `pacct/web/dashboard.py` — **only the home and `main()`** (~300 lines). The GLV used to live here (4,150 of its 4,462 lines); it moved to `pacct/web/glv/`. Still the entry point `app.py` imports (`from pacct.web.dashboard import main as web_main`).
  - `pacct/web/glv/` — the Visualizador de Lógica, one package:
    - `state.py` — `LiveState` (+ `clear()`, which disconnecting uses to return everything to indeterminate).
    - `poll.py` — the three polling threads, one per relay family (`poll_loop` 4xx, `poll_loop_fastmeter` 7xx, `poll_loop_tar` 3xx).
    - `gle_pages.py` — pages, bits and analog symbols of a GLE.
    - `notes.py` — notes, highlighter and group checkboxes, **keyed by relay name** (see gotcha below).
    - `link.py` — `RelayLink` + `LinkPool`: a lifecycle shell, refcounted across the diagrams that ask for it, that owns whichever `Transport` (telnet or MMS) the diagram picked.
    - `transport/` — the two `Transport` implementations: `telnet.py` (SEL Fast Message, and `setup_relay(ip, port, acc_password, logger)`, which takes explicit values and no longer reads `config.ini`) and `mms.py` (IEC 61850 MMS over TCP 102).
    - `mms_map.py` — loads a relay's bit → `LN$FC$DO$DA` map (project SCD first, `selfiles`'s packaged `mms_map/` fallback) that the MMS transport polls against.
    - `diagram.py` — `GlvDiagram`: one open diagram (a rendered GLE + notes + a `RelayLink` or `None`). `build_diagram()` never touches the network.
    - `handler.py` — the routes and the per-session diagram list; `GlvDefaults` holds the `config.ini` values, read once at boot.
    - `templates/dashboard.html`, `templates/landing.html` — real `.html` files, read at import (`glv.load_template`). Same `${...}` substitution as when they were raw strings in the `.py`.
  - `pacct/web/dnp_map/` — the **Editor de Mapa DNP**: `model.py` (edits as per-session diffs, never a rewritten document), `export.py` (builds the new stream bytes, then hands them to the shared `web/rdb_write.py`), `handler.py` (routes), `templates/`. The `SET_D` parser lives in `selfiles.dnp_map` (contract: `parse(b).serialize() == b`), the Compound File writer in **`cfbwrite`** (its own repository, https://github.com/GuilhermeMarini/cfbwrite — extracted from this project, and carrying its own copy of these guarantees).
  - `pacct/web/project_files/` — the **Arquivos do Projeto** tab (`/files/`): the only screen that accepts an RDB or an SCD. `library.py` is the model (a session-scoped `FileLibrary` keyed by sha256; `library_for(sessions, session)`, never a module singleton), `handler.py` the routes (including `GET /download?sha256=`), `derived.py` the way a tool's OUTPUT enters the same library, and `client.py` the `SelLibrary` picker injected into every page. The seven tools pick from it and no longer upload.
  - `pacct/web/mount.py` — mounts every tool on **one** `ThreadingHTTPServer` by path prefix (`/`, `/glv/`, `/vb-updater/`, `/vlan-mapper/`, `/gle-exporter/`, `/settings-compare/`, `/dnp-map/`), so all tools are usable at the same time in different tabs. Each tool exposes a `build_*_handler(logger, sessions) -> type` factory and never opens a socket itself.
  - `pacct/web/themes/` — **the three directions, each owning its own CSS *and* its own markup**. `tokens.py` is the only place the palette lives: one semantic vocabulary (`--bg`, `--surface`, `--border`, `--text`, `--ok`, `--s1..--s5`, `--sans`, `--radius`, …) declared once in `_TOKEN_CSS`, filled by three themes (`caderno` = Caderno de Campo, the default; `folha` = Folha de Dados; `regua` = Régua de Bornes); a theme missing a name raises at boot. `shell.py` holds only what the three mockups write identically. `folha.py` / `regua.py` / `caderno.py` each hold that direction's `DELTA_CSS` **plus** its `nav()` and `home()` renderers. `items.py` is the tool catalogue as data. `pacct/web/theme.py` is a thin re-export kept so `from pacct.web import theme as themes` still works. Tools must **not** define colours, radii, font stacks or paddings of their own — reach for a token.
  - `pacct/web/progress.py` — the progress bar. `ProgressRegistry` holds each job's stage server-side; the client runtime (`SelProgress`) is injected into every page and drives a fixed bar at the top of the viewport.
  - `pacct/web/session.py` — per-user sessions (cookie `selsid`). Every visitor gets isolated tool state **and** an isolated upload directory under `cache/sessions/<sid>/`, swept after an idle TTL (`[web] session_ttl_hours`, default 8 h). Tool handlers subclass `SessionHandler` and reach their own state via `self.sess()` and their own dirs via `self.sdir(name)`.
- `data/relay_models/*.json` — per-relay model definitions (Fast Meter layout, GLE bit-name conventions, analog symbols). Adding a new SEL model = adding a JSON here.
- `selprotopy/` — **vendored, patched** MIT library. Treat as read-only; do not modify unless the user explicitly asks. Lives at `PROJECT_ROOT` (outside `pacct/`) and is added to `sys.path` by the dashboard at startup.
- `config/config.ini` — runtime configuration: relay IP, telnet credentials, polling interval, serial port, default GLE/relay model. Many code paths read this at startup — check it first when behavior seems off. **It is gitignored** — the versioned file is `config/config.ini.example`, and `paths.ensure_config_file()` seeds one from the other on first boot (see gotcha).
- `cache/`, `rdbs/` — generated/uploaded at runtime; gitignored. `cache/rdb/<sha256>/` is the RDB extraction cache, shared on purpose (see gotcha below); `cache/sessions/<sid>/` is per visitor and wiped at boot.

## Conventions

- **Language**: user-facing strings (HTML templates, error messages shown to the user) are in **Portuguese, accented**. Code identifiers, comments, and docstrings are in **English** for new code. When editing existing files, match the file's existing language to stay consistent within a file.
- **Type hints**: `from __future__ import annotations` is used; type hints are encouraged but not strictly enforced.
- **No linting / formatting** is configured. Follow PEP 8 loosely. Do not introduce a formatter without asking.
- **Verification**: `tests/` has a pytest suite (639 tests here, all passing, as of this writing; 881 across the three repositories — see Dependencies) covering the parsers (GLE render, SCD, RDB extraction, `SET_D`, OLE rebuild), the RDB↔SCD matcher, the SELOGIC parser and comparator, the TARGET-region parsing, the Editor de Mapa DNP's model/export logic, and the distribution (what a bundle may and may not carry, and each of the updater's five rules); run it with `.venv/bin/python -m pytest tests/`. There are no `xfail` markers left: the two that used to sit here each named a real bug, both bugs were fixed, and each is now a plain passing assertion that says so where it stands (`tests/test_rdb_write.py`, `tests/test_relay_scd_match.py`, `tests/test_target_region.py`). The GLE renderer has a golden file (`tests/fixtures/render_page.svg`); regenerate it with `SEL_UPDATE_GOLDEN=1` and **read the diff**. The web tools themselves have no unit tests — verify those by launching `python3 app.py --web` and exercising the affected tool in a browser. For changes that need a live relay (GLV polling, Fast Meter), say so explicitly — they cannot be verified without hardware.

## Dependencies

`pyserial`, `telnetlib3`, `olefile`, `openpyxl`, `py61850` (see `requirements.txt`). Python 3.10+ (tested on 3.12).

**`py61850` ships as a PRE-RELEASE, and the requirement line has to say so.** The MMS client the GLV calls (`MmsClient`, `decode_data_definition`, `py61850.mms.pdu`) exists from `0.2.0.dev1`; PyPI carries that and `0.0.1`, and **`0.2.0` final does not exist**. A plain `py61850>=0.2.0` therefore matches nothing installable, `pip install -r` fails, and `app.py` `sys.exit()`s on it — a clean clone then boots **no tool at all**, not just the MMS one. The line is `py61850>=0.2.0.dev1`: mentioning a pre-release in the specifier is what lets `pip install -r` take a dev **without `--pre` on the command line** (PEP 440). It was a `@ git+...@<sha>` pin until 2026-08-31, while nothing was published; that shape still passes the test, but it costs the automatic pickup of a new dev and an upstream history rewrite orphans the sha (it did — the pinned commit is no longer reachable from `main`).

**Pulling a newly published dev is one command, and the normal boot is not it**: `python3 app.py --atualizar-deps` (`--update-deps`) runs `pip install -r requirements.txt --pre --upgrade` and exits. `install_requirements` otherwise runs pip **only when a package fails to import** — a substation has no internet, and a version check on every `--web` would turn "no network" into "nothing starts". `tests/test_requirements.py` pins both halves: the pre-release mention in the line, that `--atualizar-deps` really asks pip for `--pre --upgrade`, and that `app.py:parse_requirements` still yields an importable name.

py61850 is **AGPL-3.0-or-later** since `e515aca` (it was MIT), with a commercial option from its copyright holder. The MMS tests `pytest.importorskip("py61850")` so a machine without it loses those tests and not the whole suite.

Tests (dev only): `pytest`, in `requirements-dev.txt`. `app.py` only bootstraps `requirements.txt`, so running the suite needs one manual step: `.venv/bin/python -m pip install -r requirements-dev.txt`, then `.venv/bin/python -m pytest tests/`. This is the one exception to never running `pip` by hand.

## Gotchas

- **`config/config.ini` is gitignored; `config/config.ini.example` is what git carries.** That file is the designated place a commissioning engineer types a live substation's ACC/2AC passwords, and a password committed to a public repo is in history forever — so the tracked file is the model, with an RFC 5737 documentation IP (`192.0.2.10`) and the SEL factory defaults (`OTTER`/`TAIL`) marked as such. A clean clone therefore has no `config.ini` at all, and `ConfigParser.read()` on a missing file raises nothing: every `cfg.get(...)` would quietly take its fallback and the app would boot with the wrong configuration and no error. So `paths.ensure_config_file(path, logger)` seeds one from the model — `<path>.example` first (which covers `--config outro.ini`), then `config/config.ini.example` — logs at INFO that it did, and raises `FileNotFoundError` when neither exists. Both entry points call it before reading: `web/dashboard.py:main()` and `cli/runner.py:load_config()`.

- **selprotopy is vendored and patched** — a PreToolUse hook will block edits there. If a fix genuinely belongs in selprotopy, surface it to the user instead of patching silently.
- **Drain the login banner before handing a socket to `SELClient`** (`pacct/core/relay_conn.py:drain_login_banner`). selprotopy's `_verify_connection()` does one `read_until(b"\r\n")` per attempt with only 5 attempts, so it can cross at most 5 *lines* of banner. A relay that announces device name, date/time, station and model (e.g. SEL-311C) burns all 5 attempts inside the banner and raises `ConnVerificationFail` while answering perfectly — the failure tracks banner length, not model or network.
- **Every selprotopy private the toolkit touches lives in one class.** `selprotopy/` is vendored and hook-protected, so `pacct/core/relay_conn.py` holds both the full inventory (in the module docstring) and `FastMessageChannel`, the only code that says `_write`, `conn`, `fm_command_1`, `fast_meter_definition` or `dnaDef`. The three `poll_loop*` and `AsciiTargetReader` talk to the channel instead. Get one with `channel_for(client)`, **never** `FastMessageChannel(client)`: it memoises per client in a `WeakKeyDictionary`, and the poll loop and the target reader have to hold the *same* object — `is_clean` is the handshake that decides which of them drains the buffer before the next command. That handshake used to be `client._buffer_clean`, an attribute *this project invented and hung on selprotopy's object*; it is channel state now. One exception, deliberate: `pacct/cli/runner.py` still calls the privates directly — it is the single-relay CLI path, shares no connection, and every line of it needs a bench relay to verify.

- **TARGET region differs by relay family**: SEL-4xx exposes a TARGET memory region via Fast Message; SEL-7xx does **not** — digitals come from A5D1 Fast Meter banks. The relay model JSON's `fast_read` field controls which path is used.
- **Three `fast_read` modes, one per relay family.** `target_region` (4xx: digitals via `VIEW 1:TARGET`), `fast_meter_digitals` (7xx: digitals inside the A5D1 banks), `tar_digitals` (3xx: analogs from A5D1, digitals via ASCII `TAR <row>`). An absent/`null` value silently becomes `target_region`, so always set it explicitly on a new profile. Unknown values now warn and fall back.
- **Why 3xx needs its own mode** (measured on SEL-311C-1-R509): `MAP 1 TARGET BL` and `VIEW 1:TARGET` return `Invalid Command`; A5D1 advertises `numdigitalbank=111` but the DNA block is 111 rows of `*` (no named bits), so Fast Meter yields **analogs only**. Digitals come from `TAR <row>` — 8 named bits per round trip, ~200 ms each **on the relay** (pipelining does not help: 13 rows took 2.81 s sequential vs 2.53 s pipelined). Hence `poll_loop_tar` reads only the open page's bits (`LiveState.wanted_bits`, set by the `/values?page=` handler) and floors the interval at 1.5 s.
- **3xx bit names are NOT zero-padded**: `LT1`, `SV13T`, `RB1` — unlike the 751's `LT01`/`SV01T`. `VB001` *is* padded (3 digits). Confirmed by reading the relay's Relay Word (111 rows, 731 named bits). There are no SELOGIC counters, so the 311 profiles omit the `COUNTER` block.

- **A relay model is not an alias just because it shares a family.** The SEL-787 was an alias of the SEL-751 and should never have been: the 751 is a **feeder** relay whose `analog_symbols` match `IA`/`IB`/`IC`, `VA`/`VB`/`VC`, `IN`/`IG`, while the 787 is a **transformer differential** relay that measures per winding — `IAW1`, `IBW2`, `IGW1`, `3I2W1`, `TRIPXFMR`. Measured: of 14 real 787 channel names, the 751 profile recognised **1** (`FREQ`); the 787 profile recognises **14**. A 787 opened in the GLV therefore showed no analog symbols at all and nothing said why. The channel names come from the SEL DNP3 device profiles in `docs/dnp_r100787.zip` and `docs/dnp_r100787-4.zip` (the `-4` adds winding 3), and the patterns accept the `_MAG` suffix optionally because the 8-character DNP label limit is why SEL writes `IAW1_MAG` with an underscore and `3I2W1MAG` without. **The differential quantities themselves (IOP/IRT) are deliberately NOT in the profile**: a DNP profile documents only the factory default point map, so there is no measured name to match, and a wrong pattern would group the wrong quantity on a protection relay. They need a bench 787 and a GLV FID cache. The SEL-710 (a **motor** relay) came off the same alias list and has no profile of its own — so it resolves to `None`, which is the honest state: with no model the tool says so, with the wrong model it lies quietly.
- **The two model registries drift, and the drift has to be written down.** `selfiles`'s packaged `relay_models/` drives the GLV and the GLE tools; `selfiles`'s packaged `wordbits/` drives the DNP map's name check. Same keys, different sources, no shared loader. `tests/test_relay_models.py::test_the_two_model_registries_agree_or_say_why_not` fails on a model present in one and not the other unless it has a line in `KNOWN_ASYMMETRIES` saying why. Two live today: SEL-311L (no wordbits — no DNP profile and no GLV capture, so name validation is off and the page says so) and SEL-421 (no relay model — its DNP names validate, but nobody built the GLE/Fast Meter profile, so a 421 in an RDB will not open in the GLV).
- **GLE bit-name conventions differ by relay family**: 4xx uses `PLT##/PCT##Q/PCN##Q`; 7xx uses `LT##/SV##/SC##` without the `Q` suffix. See `data/relay_models/SEL-751.json` `_notes` for the full mapping.
- **Inside the 4xx, every protection block has an automation twin, and only the timers/counters carry the `Q`.** Protection `PLT##` / `PCT##Q` / `PCN##Q` / `PST##Q` / `PSV##`; automation `ALT##` / `ACT##Q` / `ACN##Q` / `AST##Q` / `ASV###` (three digits — ASV goes to 256, PSV stops at 64). Measured on real Relay Words (the GLV FID caches in `cache/`): a latch never has a `Q`, a timer always does. The 411L profile had `ALT##Q` copied from the timer and therefore asked for a bit that does not exist.
- **The 4xx GLE dialect is explicit; the generic one is not 4xx.** A 4xx `.gle` writes `PLT`, `PCNDTIMER`, `ACNDTIMER`, `AST`, `PCN`, `ACN`, `PST`; `TIMER`/`LATCH`/`COUNTER` are what 3xx, 2xxx and 7xx write. Measured across the whole corpus, so the generic aliases some 4xx profiles still carry are dead weight — and worse than dead when two blocks claim one: `blocks_by_xml_type` lets the LAST definition win (it warns at boot), which is how `PLT` and `ALT` both claiming `LATCH` would have turned every protection latch into `ALT##`. One XML type, one owner; `tests/test_relay_models.py` guards it.
- **A GLE connector is not an edge — it is a name, and the signal died on it.** Whoever draws the logic uses a connector so as not to drag a long line across the page, and in the XML that is two or more `<element type="Connector">` sharing one `<label>`, **with nothing linking them** (measured on `52 - Cmd. Fechar` of `QPC2_TR1_UPC1`: `667 → #723 [Cont1]` and `#206 [Cont1] → 517`). They were two independent failures: `render_gate` drew a `→` and **threw the label away** — `element_info` reads the name from `<logic_element>`, and a Connector has none, the `<label>` is a direct child of the `<element>` —, and the `switch` in `evaluatePage` fell through to `default: continue`. Measured across the 418 `.gle` of `rdbs/extracted/`: 107 use a connector, 324 elements, **110 networks, with exactly one receiver each, 110 of 110**, fan-out up to 9, and **9 networks crossing pages** (`LEDGROUND`: driven in `SCADA`, derived in `LEDS`). Four things are load-bearing: **(a)** `connectors.py` extracts **structure** (tree + bits) and the **JS evaluates** — putting NOT/RTRIG/AND in Python as well would be the same rule in two languages; **(b)** the walk stops at the first **named Relay Word bit** (`SYMBOL`, or `derived_bit_for`), which is what makes a `PCN` end honestly (the relay publishes `PCN01Q`) and what keeps the equation at ~10 bits — median 10, maximum 10; **(c)** `values(page)` adds the bits that **drive** the page's connectors, and those were already in `all_wanted_bits` (the whole GLE), so neither `ensure_bits` nor the MMS map changes — what was missing was the per-page filter narrowing them back down; **(d)** the legend colours only the tokens the network itself declared as a bit, and not by the shape of the identifier: a SEL name starts with a digit (`52A`, `89CL01`) and a counter's preset `6` is no bit at all. A network without a single receiver is ignored with a log — guessing which end drives it would paint a line on a hunch.
- **Themes are a cookie, not session state.** `seltheme` (`folha` | `regua` | `caderno`), one year, set by `POST /theme`. Cookie and not session because the theme should survive a new session and follow the visitor across all nine screens. No cookie → `[web] theme` from `config.ini` → `caderno` (`themes.DEFAULT_THEME`, the one place the factory default lives). `mount.py:inject_head()` adds `<link rel="stylesheet" href="<prefix>/theme.css">` and stamps `data-theme` on `<html>` for **every** page, including the home at the empty prefix. **The picker itself is mounted only on the home** (empty prefix): it used to be appended to every page's `<header>`, and in an application header like the GLV's — title, IED, state, search, tools, zoom — it was one more group fighting for a band that already wrapped. Choosing once, in the menu, is enough: the cookie lasts a year and follows the visitor across all nine screens.
- **The three themes do not share markup, only tokens.** The mockups in `mockups/{06-folha,03-regua,10-caderno}/` are the reference, and they disagree structurally: on the home only 7 of 53 classes are common to all three. The menu is a numbered reference table in folha, sticky-note cards with a clip in caderno, and wire-coloured borne cards in régua; the navigation is `.toc`, `.tabs`/`.tab` and `.strip`/`.borne` respectively — different DOM, not the same DOM recoloured. So screens carry markers (`<!--NAV:<key>-->`, `<!--HOME-->`) that `mount.py:_resolve_markup()` resolves **per request**, with the visitor's theme in hand. Never bake a nav into a page string at import time: that is what froze folha's markup into all three themes. A screen that needs to differ per direction gets a renderer in the direction's module, next to the CSS that paints it.
- **`/theme.css` and `/static/...` are served by the dispatcher**, like `/progress` — never by a tool. Both answer with and without a mount prefix. The nine `.woff2` in `pacct/web/static/fonts/` ship with the project on purpose: a substation may have no internet, so **never link a CDN**; `themes/__init__.py` folds `fonts.css` into `/theme.css` with absolute `/static/fonts/` URLs. The OFL licences in `licencas/` and `NOTICE.md` must keep travelling with the files.
- **The GLE drawing never changes with the theme.** The SVG comes from `parsers/gle.py:render_page()` with its own stylesheet; the live-state classes (`bit-1` / `bit-0` / `bit-unknown`, `polyline.connection`) and the highlighter / search overlay colours stay literal in `dashboard.py`. Only the frame around the drawing is themed (`--viewer-bg`).
- **Web dashboard binds to `0.0.0.0:8765`** by default. Only this one port is served — every tool lives under a path prefix on it.
- **Uploads happen in exactly one place.** `/files/` is the only screen with a drop zone; every other tool shows a `SelLibrary.picker` over the same library. A tool whose selection does real work (reading an SCD, listing a relay's GLEs) keeps a `/select-rdb` / `/select-scd` route — the tail of its old upload handler, everything after `process_upload`/`load_scd` returned — and calls it from the row click; a tool whose selection was only bookkeeping has no such route at all (see the next bullet). Adding a tool means writing that tail, never another upload panel. The 500 MB / 200 MB ceilings live once, in `project_files/library.py`. The drop zone takes **several files at a time** and uploads them one after the other: two 140 MB RDBs in parallel fight over the substation's bandwidth and over the same progress job, and one bad file in the selection must not stop the rest from entering the project.
- **A tool's output goes back into the project, and that is the only path between two tabs.** `SessionHandler.publish_output()` → `project_files/derived.adopt()` is the other half of `/files/upload`: the seven places that write a file (`vb_updater` ×4, `gle_exporter` ×2, `dnp_map:/export`) hand it over, and it lands in the same library an upload lands in, by the same rules — keyed by the sha256 of the content, RDB through `process_upload` into the shared `cache/rdb/<sha256>/`, everything else copied into the session's `files/<sha12><ext>`. Before this the only way to feed a corrected SCD into the next tool was to download it and upload it again: 140 MB across the substation's network to move a file between two tabs of the same server. Three points that are deliberate: **(a)** adoption is best-effort and never breaks the export that triggered it — a failure is a logged string and a `project_file: null`, and the tool's own download link still works; **(b)** `.xlsx` enters as `KIND_XLSX`, which `library.kind_for` does NOT know, so a spreadsheet can never be *uploaded* into a project and no picker (`?kind=rdb|scd`) ever offers one — it is kept only so the files a tool produced can be found and downloaded from one place; **(c)** provenance is `FileEntry.origin`, a field of its own and not a suffix inside `detail` — `detail` says what is *inside* the file ("27 IED(s)"), and the two are shown differently (a chip in the listing, a `· gerado no X` suffix in the picker's line). The tools announce it with `SelLibrary.savedNote(data.project_file)`, written once in `client.py`.
- **Output names come from the display name, never from the file on disk.** The library stores an SCD as `<sha12>.scd`, so the VB Updater deriving its output name from `st.scd_path` handed the user `72586aeda11e_descriptions.xlsx`. It reads `st.scd_name` now. Any new output name has the same trap.
- **`/files/download?sha256=` is not the tools' `/download?file=`.** The tool route takes a PATH from the request and is therefore sandboxed to the session's own dirs — which is why it cannot serve the shared RDB cache. The library route takes a sha256 and looks it up in *the caller's own library*: there is nothing to sandbox because there is nothing for the client to point anywhere, so it can hand back an RDB out of `cache/rdb/`. It streams in 1 MB chunks (an RDB is 40–140 MB) and names the file with RFC 5987 `filename*=UTF-8''`, because these names carry accents.
- **The upload input is thrown away and rebuilt after every batch** (`rearmInput()` in `library.html`). `input.value = ''` is not enough and was the bug: the element keeps the previous selection, the OS dialog reopens on top of it, and on the second upload it came back with the last file still selected — "Abrir" lit up only for *that* file, and clicking a different `.scd` did not change the selection. A freshly cloned element has no past. It is rebuilt in the batch's `finally`, never inside the `change` handler: mutating the input while its own `change` is still on the stack is what dirtied the state in the first place. Rebuilding also restores what `value = ''` was there for — re-picking the same file still fires `change`.
- **The upload input deliberately has no `accept`.** `accept` is what builds the OS file dialog's type filter, and the dialog *remembers the filter from last time*: on a second upload it reopened narrowed, the `.scd` vanished from the listing and "Abrir" was greyed out — the user could see their file and could not send it. The type check did not go away, it moved into the page: `kindFor()` in `library.html` mirrors `library.kind_for` (same extensions, lowercased, so `.SCD` works) and refuses a wrong pick before a byte is sent, with the server refusing again behind it. A dialog that shows everything beats one that hides the right file.
- **The library is keyed by content, and it dedups twice on purpose.** `rdb.process_upload()` dedups the *extraction* across visitors and restarts (`cache/rdb/<sha256>/`); `FileLibrary` dedups the *entry* within one visitor's project. A second upload of the same bytes returns the existing entry and keeps the FIRST name — renaming an entry under a tool that is already showing it is worse than ignoring the second name. RDB bytes never reach the session directory; only SCDs do, at `cache/sessions/<sid>/files/<sha12>.scd`.

- **A duplicate upload must never delete the file, because it is the SAME file.** `/upload` writes first and checks for a duplicate after — it has to, the sha256 is only known once the last byte arrives — and `files/<sha12>.scd` is named after the CONTENT, so the second upload of an SCD the project already has rewrites the existing file byte for byte rather than making a second one. `_discard()` deleting "what this upload built" therefore deleted what the library was pointing at: the entry stayed in `FileLibrary` (memory) with nothing behind it on disk, so the picker kept offering the SCD, `/select-scd` answered `Arquivo não está mais no projeto`, and the log said `SCD nao encontrado` for a file the screen was showing. Re-dropping a pair of files to add the RDB beside the SCD is the ordinary way in. `_discard(entry, keep=existing)` now spares a path the surviving entry owns, and still deletes a build no entry claims. `derived.adopt()` never had the bug — it checks the duplicate BEFORE writing — and the RDB half never did either, because its `_discard` is deliberately a no-op (`cache/rdb/<sha256>/` has no owner). `tests/test_project_files.py` pins both halves plus the `keep=` at the call site, which is one keyword whose loss is silent.
- **The library's directory is `Session.subdir("files")`, never `SessionHandler.sdir("files")`.** `sdir()` prefixes the caller's `session_key`, so using it would hand each tool a different directory and silently un-share the library. Derived outputs still go to `self.sdir("out")`, and `/download` stays sandboxed there.
- **Infrastructure routes never create a session.** `/library`, `/progress`, `/theme.css` and `/static/...` are answered *before* `_dispatch` resolves a session, via `SessionManager.peek()` (reads a session, never mints one). They own no state — a stylesheet is not a visitor. When they did mint, every cookie-less one added a phantom session, and once the dispatcher also started emitting `Set-Cookie` each of those responses handed the browser a *different* fresh identity; concurrent requests then traded the identity between them and each upload landed in a new empty project, so the file list looked like it kept being replaced. The tell in the log is the same sha256 logged as newly added twice — only possible across two sessions. `/library` with no session answers `{"files": []}`, which is the truth. Only a tool's own page mints a session.
- **A route the dispatcher answers itself still has to emit the session cookie.** `Dispatcher` is a plain `BaseHTTPRequestHandler`, not a `SessionHandler`, and it answers `/library`, `/progress`, `/theme.css` and `/static/...` without swapping `self.__class__` — so those responses used to skip `SessionHandler.end_headers` and never sent `Set-Cookie`. A cookie-less request to one of them created a session server-side that the browser was never told about, so the next request created another, and whichever request finally reached a tool handler minted the session that stuck — stranding everything uploaded under the earlier ones. On screen the project simply emptied and only the last file survived. The one that still needs it is the `"/vb-updater"` → `"/vb-updater/"` redirect, answered by the dispatcher *after* `resolve()`; `Dispatcher.end_headers` now mirrors `SessionHandler`'s, and the two never run on the same response, so there is no double `Set-Cookie`.
- **`/library` is served by the dispatcher**, like `/progress` and `/theme.css` — with and without a mount prefix, filtered by `?kind=`, and without ever creating a session. The empty state links `../files/` **relatively**: a cross-page `<a href>` is one of the two things the `fetch` shim cannot reach.
- **Choosing a file is one click, and there is only ever one list of files.** `SelLibrary.picker` renders the project's files as a **list you click** — no `<select>`, no "Usar" button — because the button was confirming a choice already made. Behind it there used to be a second registry: every tool kept the RDBs it had "adopted" (`st.rdbs`) and its routes answered 404 for any key that wasn't there, *even with the file in the visitor's own library*. That was the last stone of the era when each tool had its own upload. Now `SessionHandler.library_entry(ref, kind)` resolves a full **or short** sha out of the visitor's library (the short one is what tool URLs carry, e.g. `?rdb=0f5f8eff0d07`), `st.rdbs` is a cache instead of a gate, and the two tools whose selection did nothing else — **Editor de Mapa DNP** and **Comparador de Ajustes** — dropped `/select-rdb` entirely: their list routes (`/rdbs`, `/state`) enumerate the *project's* RDBs and register them while listing, so a row click goes straight to `/relays`. The four tools whose selection does real work keep their route and call it from the click. Two consequences worth keeping: a tool's list may annotate a row with what only it knows (`annotate` — the DNP map shows pending edits per RDB) but must not repeat what the library already prints (`detail` is already "27 IED(s)"); and `picker.select(ref)` remembers a selection asked for before `/library` answered, so restoring "the RDB you were on" marks the right row instead of silently missing it.

- **`SelLibrary` is injected into the `<head>`, and `SelProgress` before `</body>`, and the difference is not cosmetic.** Every tool calls `SelLibrary.picker(...)` at the top level of its own `<script>`; a runtime defined after that script has not been parsed when the call runs, the `ReferenceError` aborts the whole inline block, and the tool comes up **blank** — not just the picker, everything the script was going to render. `SelProgress` survives at the tail of the body only because nothing touches it outside an event handler. A new page-wide runtime whose API is called during page setup goes in the head.
- **Arquivos do Projeto is a nav entry, not a tool.** It is `items.FILES_ITEM` beside `MENU_ITEM`, never in `TOOLS` — it has no `funcao`/`entrada` to declare and would inflate the home's counts. Tool numbering stays 1..9 (régua's home cards read "Borne *i*" and must match its strip), so Menu keeps `0` and Arquivos takes `A`.
- **The menu is grouped by what a tool eats, and two groups ship empty.** `themes/items.py` carries `GROUPS` (geral → SEL → GE → Siemens) and every `Tool` declares its `grupo`, required and without a default — the same reason `fast_read` has none. `TOOLS` is sorted into group order and `ORDINAL` is the one source of the 1..9 number, because six renderers print it and régua's strip and cards have to agree. GE and Siemens are declared with no tools and a `vazio` line saying what will land there: empty and silent is vapour, empty with a roadmap is a forecast.
- **What did NOT move into the library:** the XLSX round-trips (`gle_exporter:/import`, `vb_updater:/import-descriptions`) take back a spreadsheet the tool itself produced, and `dnp_map:/import-profile` writes project-wide reference data into `selfiles`'s packaged `wordbits/`. None of the three is a project INPUT; all three keep their own upload control. That is about uploads only — what those same tools *write* does enter the library, through `derived.adopt`.
- **Tool handlers keep absolute routes** (`/state`, `/download`, ...). The dispatcher strips the mount prefix and swaps `self.__class__` before delegating, and `inject_prefix_shim()` patches `fetch`/`XMLHttpRequest` in the served HTML to re-add it. So when adding a tool, write routes and `fetch()` calls as if it owned the root. Two exceptions the shim can't reach — prefix them with `self.mount_prefix` by hand: URLs the browser navigates to directly (`download_url` in an `<a href download>`), and cross-page links (use a relative `./` instead).
- **The GLV opens N diagrams at once, and each starts disconnected.** The list of open diagrams is per visitor (`dict[id, GlvDiagram]` in the session, like the other four tools); the connection is not. `LinkPool` keys one `RelayLink` per `ip:porta` for the whole process and refcounts it: the second diagram pointing at the same relay joins the existing telnet, and it only closes when the last one lets go — a SEL relay accepts few simultaneous sessions. `owners` is a **set of diagram ids**, not an integer, so a double click on Conectar/Desconectar can't close the telnet under a live diagram or leave a connection dangling. Ceilings in `[web]`: `glv_max_links` (10 new connections in the process) and `glv_max_diagrams` (10 per visitor); joining an existing connection never counts against the ceiling.
- **The `LiveState` belongs to the `RelayLink`, not to the diagram** — the `poll_loop*` write into a single object and a relay's Relay Word is the relay's, not the drawing's. A diagram displays `link.state` when connected and its own empty `idle` state when not; disconnecting is a pointer swap plus `clear()`, which is why nothing on screen can keep showing a reading that isn't happening.
- **Connecting can't block the response.** `POST /connect?d=` answers 202 and the work runs in a thread — on a fresh FID the `AsciiTargetReader` takes minutes to map name → (row, bit). Progress goes through a job per diagram (`glv-connect-<id>`), and a failure leaves the diagram **open and disconnected** with the reason on the badge. `RelayLink.connect` has a watchdog (`[web] glv_setup_timeout`, 60 s) that closes the socket if login/autoconfig hangs; it deliberately does **not** cover bit discovery.
- **A second diagram on a live connection needs `ensure_bits()`**, which stops the polling thread, runs the discovery and starts it again. The telnet is one, and interleaving `TAR <name>` with the Fast Meter pipeline scrambles both replies.
- **The GLV's tab strip wraps; it does not scroll sideways.** `#tabs` was one nowrap row with `overflow-x: auto`, which is invisible until the ceiling is used: at 10 diagrams half the tabs sat off-screen behind a horizontal scrollbar nobody looks for, and the strip gave no sign there were more. It is `flex-wrap: wrap` now, like `#pages` right below it has always been — the grid row is `auto`, so the strip grows in height on its own. Two details hold it up. The `white-space: nowrap` moved from the STRIP to the ITEM (`#tabs .tab, #tabs .tab-new`), so it breaks between tabs and never inside one tab's name. And `#tabs .tab .label` caps the name with an ellipsis, because wrapping between tabs cannot save you from ONE tab wider than the viewport — a flex item does not wrap within itself — while the full relay/GLE/IP is already in the tab's `title`. Measured in the browser with 10 tabs: 2 rows at 1908 px, 4 at 900 px, 10 at 420 px, `scrollWidth == clientWidth` in all three, and a forced 64-character name clipped to 135 px instead of pushing the strip open.

- **A GLV tab remembers the page it was showing, and that memory is the diagram's, not the browser's.** Switching tabs does not reload: the client fetches `/meta?d=` and re-renders the page strip and the viewer from `meta.initial`. While `initial` was always the GLE's default page (the SECOND one — page 1 is a cover/index in almost every QuickSet file of the corpus), whoever was on page 27 of a 41-page GLE landed back on page 2 on every trip between two relays, and again after an F5. `GlvDiagram.open_page` holds it, `default_page()` is the old behaviour under a name, and `meta()` prefers the first over the second. It is recorded in `GET /pages/<safe_id>` — the ONLY path to a page's SVG, travelled by both the page-strip click and the variable search's cross-page navigation, so there is no way to open a page without it being seen. Two guards earn their keep: an id that is not a page of THIS GLE is not remembered (the value comes off the URL), and a remembered page that no longer exists falls back to the default instead of opening an empty viewer. Server-side and not `sessionStorage` because the diagram list already lives there — the page is diagram state like `interval_ms` or the notes key.

- **The GLV has one page** (`/glv/`) with a tab strip; the GLE selector is the separate page `/glv/novo`. `GlvMount`, `_glv_activate` and the blocking `_glv_session_loop` are gone, and so is "Trocar GLE" — you open another diagram instead of replacing the only one.
- **Notes, highlights and group checkboxes are keyed by the relay's name in the RDB** (`cache/notes_<name>.json`, `groups_`, `highlights_`), not by DEVID — the name exists before any connection, so a note written while disconnected is already in the right file. On the first successful connection `NoteStore.adopt_devid()` adopts what an older run wrote under the DEVID, per file, and only when the file under the new key doesn't exist. `NOTES` is a process-level registry: two visitors on the same relay must share one object and one lock.
- **RDBs go to a shared content cache; everything else stays in the session.** `rdb.process_upload()` extracts into `cache/rdb/<sha256>/` — same bytes, same file, so the extraction is reused between visitors and across restarts, and `meta.json` is only written once extraction finishes (an entry without it is a broken extraction and is redone). The cache has no owner, so `rdb_cache.sweep()` runs with the session sweeper: age (`[web] rdb_cache_max_age_days`), then size (`rdb_cache_max_gb`), never touching an entry younger than `session_ttl_hours`. The name on screen comes from `RdbInfo.display_name` (what *this* upload was called), never from the cached path. **Derived outputs still go to `self.sdir("out")`** (and from there into the library, see `derived.adopt`), and the tools' `/download?file=` is sandboxed to the session's dirs — putting the shared cache inside that sandbox would let one visitor download another's generated file.
- **Uploads must go through `SelProgress.upload()`, not `fetch()`.** `fetch` cannot report upload progress; only `XMLHttpRequest.upload.onprogress` can, and RDBs are 40–140 MB. For long server work with no request body to measure, use `SelProgress.post()`.
- **Long server-side work should report stages.** The client sends `X-Job-Id`; the handler calls `self.job()` and reports via `.stage()` / `.fraction()` / `.finish()` / `.fail()`. `/progress?job=<id>` is served by the dispatcher for every mount, and answers in parallel with the in-flight POST because the server is threaded. `self.job()` is a no-op when no job id was sent, so handlers need no branching.
- **Session state is per-user, so module-level singletons are a bug.** Tools must not keep `_state = _SessionState()` at module scope; helper functions take the state as a parameter instead (see `_state_payload(st)`).
- **`RdbInfo.relays` only lists a relay that owns a `.gle` file.** `selfiles.rdb` builds a `RelayEntry` from the `.gle` streams, so a relay with settings but no diagram — a SEL-2440 data concentrator, for instance — never shows up there, even though its DNP map is exactly what someone wants to edit. Anything that needs every relay walks `extract_dir/Relays/` directly instead; that's what `parsers/set_dnp.py:discover()` does.
- **A `SET_D` line ends `KEY,"VALUE"\x1c\r\n`.** The `0x1C` (File Separator) sits *inside* the line, before the CRLF, and is not whitespace; `parsers/sel_settings.py` doesn't strip it and leaves the byte stuck to the value, which is fine for reading and fatal for writing. Anything that rewrites a settings file goes through `selfiles.dnp_map` instead, whose contract is `parse(b).serialize() == b`. DNP point-index padding isn't consistent either: the 411L writes `BI_1`, the 751 and the 2440 write `BI_00`, and the free-slot marker differs the same way — `""` on the 411L, `"NA"` on the 751/2440. The key text is always preserved literally, never rebuilt from the index.
- **`olefile.write_stream` only swaps a stream for one of the exact same size.** Rearranging a DNP map conserves the byte multiset, so it always fits; filling a free slot grows the file, so it never does. **`cfbwrite`** (a separate library, extracted from this project) reconstructs the whole Compound File for that case. It verifies its own output before handing it over — reopens the result and compares every stream against the source — and writes atomically: the new container is built in a temp file beside the destination, then `os.replace`d into place, so a failure anywhere leaves the destination exactly as it was, and it refuses outright to rebuild a file onto itself. A bug in the writer has to surface as a failed export, never as a silently corrupt relay settings file. There is deliberately no path that pads a settings file with whitespace until it fits — nobody here knows what AcSELerator QuickSet tolerates.
- **Every RDB write goes through `pacct/web/rdb_write.py`, and none pads XML to fit.** `olefile.write_stream` swaps a stream only for one of exactly the same size, and the VB Updater and the Exportador de Comentários GLE used to meet that by collapsing inter-tag whitespace across the whole `.gle` (`>\s+<` → `> <`) and injecting a padding `<!-- -->` before `</editor>` — mutating a settings file in a way nobody had confirmed AcSELerator QuickSet tolerates, and against the policy stated for the DNP path. All three tools now call `rdb_write.write_streams()`: `write_stream` when every replacement keeps its size, `cfbwrite.rebuild()` when any doesn't, always atomically onto the destination. `_fit_xml_to_size` is gone and `tests/test_rdb_write.py::TestNoPaddingPathCameBack` asserts neither tool has it back or touches `olefile` directly. **Measured cost of the old path**, from the tests that pinned it: growing one comment rewrote element 544 — never mentioned in the update — because the collapse is global; shrinking one emitted `<!--            --></editor>`.
- **A tool that writes an RDB reads first and writes once, and a partial apply is a failed apply.** Both migrated tools now do a read-only pass that resolves every stream and computes its new bytes, then one write. Before, the output RDB was `shutil.copyfile`'d up front and each selection written into it as it went, so a failure on the third left the first two in the file — and `update_rdb_with_scd_descs_batch` still answered `ok: True`, after which `publish_output()` put that half-applied RDB into the project library where nothing distinguishes it from a complete one. The per-selection `results` still go to the screen on failure, so the user sees *which* one broke; what they don't get is a download link to a file that is half right.
- **A rebuilt RDB comes out much smaller, and that is correct.** One real corpus RDB measured 142.9 MB → 36.9 MB after a no-op rebuild (no edits at all). QuickSet never compacts, so a real RDB accumulates thousands of orphaned, unreachable directory entries over its editing history. This was proven, not assumed: the orphan set is a disjoint island — no pointer crosses between it and the reachable set in either direction, and no storage entry is itself orphaned — and the corpus holds two QuickSet saves of the same substation whose reachable path sets are identical, 1092 paths either way, so QuickSet's own compacted save keeps exactly what this traversal keeps.
- **A DNP map travels between relays only when the RELAYTYPE is the same string.** A substation is banks of identical relays, so one session's map copies onto other relays — and onto relays in **another RDB**, which is the interesting case: the map was fixed in last week's file and the bank that needs it is in today's. `model.copy_map_to` therefore takes a source `(rdb, relay, session)` plus the parsed source file and a **separate** destination rdb key; the edits are recorded under the DESTINATION, so they belong to that RDB's own "alterações pendentes" and leave in that RDB's own export, and nothing is written into the source. `copy_session` (the editor's "Aplicar às demais sessões") is the same function with both keys equal, which is also what makes the "skip the source" guard rdb-aware: `R1/D1 → R1/D1` is a no-op inside one RDB and a real copy across two.

  The gate is `set_dnp.same_model`: exact comparison of the two SET_D `[INFO]` RELAYTYPE strings, only normalised for blanks and case, and an empty one matches nothing including itself. Deliberately NOT the lenient family match `wordbits._key_variants` does — that one looks for a *name domain*, where falling back from `SEL-411L-A` to `411L` costs nothing, while the option suffix is exactly what changes the I/O board and with it how many BI/BO points the file has. Three more things hold it up. **(a)** Only points travel (`points()` plus each point's `sca_key`/`dbd_key`); `extras()` — MINDIST, MAXDIST, the session's own configuration — never does, or a copy would rewrite the target's DNP session while claiming to copy its map. **(b)** Each target is diffed against its OWN original, so a target that already matched gains nothing and the pending count stays honest — measured on the corpus 27-relay RDB: 14 SEL-751, one D1 onto the other 13, 356 fields on 9 relays and "já era igual" on 4. **(c)** `CopyOutcome` counts `missing`/`extra` (source keys the target lacks, target points the source never names) and the screen shows them; both are 0 between two files of one model across the whole corpus, and they exist so a firmware that disagrees says so instead of leaving a half-copied map that looks complete. The route validates every target before writing any, so a rejected list writes nothing.

- **In the DNP map's table only the `⠿` cell starts a drag.** The row is `draggable=false` at rest; the handle's `mousedown` arms it and `dragend` (plus a document-level `mouseup`, for a press that never became a drag) disarms it. `draggable` has to live on the `<tr>` — that is what gets dragged and what becomes the drag image — so arming and disarming it is the only way to have both. With the row permanently draggable, click-dragging across a point's text did not select it: the browser hands the gesture to drag-and-drop as soon as the pointer moves with the button down inside a draggable element, so copying a variable name out of the map was impossible on a table whose whole purpose is editing those names.

- **The cross-relay copy is a three-step wizard of its own (`GET /dnp-map/copiar`, `templates/copy.html`), built on the Comparador de Ajustes' shell.** Origem (RDB list + IED list + the session), **pontos** (the source map, one tab per block, every point checked by default), destino (RDB list — possibly another file — + the same-model IEDs, and whether to write only the source-named session or all of the target's), confirmação (source, model, how many points of how many, destination, and the table of exactly what will be written), then Concluir. The point step exists because a bank of identical relays often shares the binaries and diverges on the analogues, or needs only the block that was just corrected: `copy_map_to(..., point_keys=…)` filters by BASE key while a chosen point still carries its `AI_SCAn`/`AI_DBDn` (the scale is an attribute of the mapped quantity, not a point of its own — same rule as a drag in the editor). What is left out is left ALONE in the target: a copy never blanks a point, so with a partial selection `extra` is not counted at all — the points the user deliberately excluded are not a mismatch to warn about. The route refuses a key that is not a point of that session rather than ignoring it: from the API, a stray key means the client is talking about a different map. It is not a panel in the editor: the editor is one relay's 380-row table, and a control that writes twelve other relays — in another file — has no business hiding in its toolbar. Three details worth keeping: the RDB rows and the confirmation show the short sha next to the name, because two files of a project routinely share a display name and only the content key says which one gets written; the destination list sorts eligible IEDs first while still SHOWING the others greyed with a reason ("outro modelo", "é a origem"), since "that relay isn't here" and "that relay won't do" are different answers; and the IED rows are a CSS **grid**, not flex — with `flex:1` on the name each row broke its columns at a different x and the list read as running text instead of a table (the Comparador's relay list had the same bug and the same fix). Entry points are on the relay list (`/dnp-map/`): a card link, and a `Copiar` link per row that opens the wizard with that relay as the source.

- **Which DNP blocks the name check judges is per model, and it is data.** `data/wordbits/<MODEL>.json` has two halves from two sources that are *not* interchangeable. The **SEL DNP3 device profile** (`selfiles.dnp_profile`, the zips in `docs/`, regenerated by `tools/wordbits_from_dnp_profile.py`) fills `kinds.{BI,BO,AI,AO,CO}` — the vendor's default point list. The **Relay Word** (`tools/wordbits_from_glv_cache.py`, from a GLV `cache/<FID>.json`) fills `bits`. A BI point can be mapped to *any* Relay Word bit and a profile documents only the factory default map, so a profile alone cannot judge BI: measured over the whole real corpus, profile-only leaves 28.6% of BI values unrecognised, and the Relay Word leaves 0%. The file's `check_kinds` therefore lists exactly the blocks its own data covers, and `wordbits.check(value, kind)` returns `"ok"` for every other block. Shipped policy, all measured: **BI** only when `bits` is present; **BO** always (0.00% once the `<close>:<open>` pair is split and the Relay Word unioned in); **AO** and **CO** always (0.00%); **AI** never (4.39% — math variables `MV`/`AMV` and fault quantities `FIA`/`FIB` are absent from the vendor's default list). Final figure across `cache/rdb`: 173,046 values checked, **0** false positives. No file for the model turns validation off entirely and the page says so; a user can supply one through **"Importar perfil DNP"** on `/dnp-map/`, which writes into `selfiles`'s packaged `wordbits/` and calls `wordbits.invalidate()`. The two generators never overwrite each other's half and are commutative. The duplicate check is domain-independent and runs on every block regardless.
- **The `<!--NAV:...-->` marker belongs as the first child inside `<div class="shell">`, not inside `<header>`.** In régua, `.shell` is a two-column grid whose first column *is* the nav; a marker left in the header collapses the whole page to about 200px wide. Folha and caderno use a single-column shell, so only régua is sensitive to this — but it is easy to get wrong when a new screen is scaffolded by copying `<header>` from an existing one instead of `.shell`.
- **`sAddr` is the only bridge, and the relay does not serve it.** Verified on a live SEL-451-5 R331: `PLT1GGIO1$DC$Ind01$d` answers `object-non-existent`. So the MMS map comes from a file — the project SCD first, `selfiles`'s packaged `mms_map/` as fallback — and there is no MMS equivalent of `TAR <name>`.
- **The FC comes from the relay, not from SCL templates.** `sAddr` sits on a `DAI` while the functional constraint lives on the `DA` in the `DOType`. Matching `LN$*$DO$DA` against `GetLogicalDeviceDirectory` resolves the FC and verifies the entry at once. `ST` wins over `MX` over `CO` — `LocSta` really is at both `CO` and `ST` on the 487E.
- **MMS reads the open page's bits in ONE batched Read, not one Read per `LN$FC`.** `MmsPoint.item` is already a full `LN$FC$DO$DA` the relay's own directory confirmed, so the poll loop hands the whole page to `read_refs` (py61850 ≥ `dcbc20c`) and the client splits it into as many requests as the negotiated `max_pdu_size` needs — 1055 leaves went out as 5 requests. Measured on three bench relays — 751 (R402), 487E (R323), 451-5 (R331) — old path → batch, by page **shape** (a drawing asks for BITS, and they land scattered across `LN$FC`): 80 scattered bits **190 → 5.8 ms** (751), **214 → 25 ms** (487E), **298 → 22 ms** (451); 200 scattered, 242 → 13.7, 376 → 58, 437 → 53 ms; the whole map, 400 → 72 ms (1055 bits), 612 → 320 ms (784), 948 → 435 ms (1422). Same values both ways, **zero differences on all three**. The one shape the batch **loses** is a page whose bits sit in few containers, and only on the two 4xx (8 containers: 42 → 63 ms on the 487E, 36 → 53 ms on the 451) — the request grows to ~10 kB fragmented over a 1024 B TPDU while the old path was 8 short reads; both sides are under the default 100 ms period, so at the default the loop sleeps the same either way (there is no floor any more — see the next bullet — so a page asked for at 0 ms would show the difference), and a real page is the scattered one (80 bits land in 50 containers on the 451). Two things follow. **(a)** Batch **leaves, never containers**: py61850 budgets the REQUEST against `max_pdu_size` and the RESPONSE is not in that sum — 16 containers already answer ~11.2 kB against a 12000 ceiling and 32 come back `MmsError: service/3`, while a boolean leaf answers ~6 bytes. **(b)** A failed access arrives as `{"error": ...}` **in place of the value**, not as an exception, and `int(bool({...}))` is 1 — a bit painted ON that nobody read. It has to be dropped from the payload so the diagram paints it indeterminate. The open-page filter stays (like the 3xx TAR mode) and is now per bit: asking for one bit used to drag in the other 30 of its container. What went away with the container reads: `get_data_definition` per container at connect (0.53 s for 194 on the 751, now 0.03 s), the positional `decode_container`, and the refusal for a firmware that would not describe a bare `LN$FC` — that failure mode does not exist when nothing asks.
- **The screen has its own cadence, it follows the diagram's read period, and its 100 ms floor is a repaint budget — not the protocol floor that was removed.** `setInterval(pollValues, 500)` was 2 Hz flat, whatever the relay was doing: with MMS at 10 ms, **49 of every 50 readings died without reaching the drawing**, because nothing between the poll loop and the browser accumulates — `state.digitals` only ever holds the LAST reading. Measured end to end before touching anything: the relay answers in **1.5 ms** (on the wire, from the field pcap), `d.values(page)` costs **0.03 ms** with a 0.6–0.9 kB payload, the HTTP round trip is **0.96 ms** (loopback, and every request opens a new TCP connection — `protocol_version` is never set, so it is HTTP/1.0), and one full `applyValues` in Chrome on the heaviest page of a real 411L GLE (440 SVG elements, 41 symbols, 28 blocks, 63 connections) is **0.80 ms with recalc and layout in the count**. Total ~3 ms against **0 to 500 ms of waiting**. The wait was the whole latency, so that is the only thing that was changed: `screenMs` now comes from the active tab's own `interval_ms` (which `tab()`/`meta()` already sent for the period control), clamped to **[100, 500] ms**, and the loop is a self-scheduling `setTimeout`. Verified in the browser: a 500 ms diagram polls 8×/4 s, a 100 ms one 38×/4 s, a 10 ms one 40×/4 s (the floor), never more than **1 request in flight**, and a request left hanging costs exactly one call and resumes on its own — the next tick is scheduled BEFORE the `await`, so a stalled fetch cannot stop the screen's clock the way a naive `await` loop would. Three things not to undo: the floor is 100 ms because 0.8 ms of repaint every 100 ms is ~1 % of a CPU and the eye gains nothing below that (the relay defends itself by answering at its own pace — the browser of the person commissioning has no such defence); the ceiling stays 500 ms even for a slower read period because the badge shows the reading's AGE, which has to keep ageing on screen while no bit moves; and the client-side waste that is still there — `evaluatePage` rebuilding the topology from DOM attributes every turn, class writes with no diff, four `innerHTML` rebuilds — was measured and left alone on purpose: it is inside those 0.80 ms, so rewriting it would buy nothing and risk the evaluator. If the screen ever needs to go faster than 10 Hz, the next lever is SSE plus `protocol_version = "HTTP/1.1"`, not micro-optimising the repaint.

- **Every duration in the polling path is `time.monotonic()`, and the reason is measured, not theoretical.** On this machine the WSL wall clock sat **82.5 s behind the Windows host clock** and periodically resynced, so `time.time()` jumped in both directions — the GLV log has its own proof, timestamps going BACKWARD (`15:19:12` printed before `15:18:29`). Two things broke, and both looked like the relay. **(a)** `cycle = time.time() - t0` read **82.3 s** on the turn that straddled a forward jump (that is the `pior 82313 ms` in the field log, three times, all ~82.3 s); on a backward jump the same subtraction is **negative**, and `sleep_for = max(0, effective_interval(interval, cycle) - cycle)` becomes `interval + 82 s` — **the loop sleeps 82 seconds**. That is the "polling travado" with a Wireshark capture that shows nothing wrong: the capture of the same session is a metronome, one Read every 10.1 ms, 96 requests/s, median answer 1.5 ms, no gap over 25 ms, 43 s straight. The freeze was never on the wire, and it predates the removal of the period floor (with the 100 ms floor the same jump gave `0.1 + 82 s`). **(b)** `age` on the badge was `Date.now()/1000 - values.ts` — a subtraction **across two clocks**, the browser's (Windows) minus the server's (WSL): a permanent skew shows as "valores antigos (82,5s atrás)", painted stale, while the values underneath are updating fine. `LiveState` now carries `last_update_mono` beside `last_update_ts` (`mark_updated()` writes both under the caller's lock) and `snapshot()` answers `age` computed server-side, `None` when nothing was read yet. The wall clock survives only where it means *an hour of the day*, never a duration: the four poll loops, the Fast Message response deadlines in `poll.py`, `core/relay_conn.py` and `core/target_region.py` are all monotonic now. `tests/test_mms_transport.py::test_a_wall_clock_jump_does_not_stall_the_poll_loop` fakes the jump (a `time` shim whose `time()` drops 82.5 s while `monotonic()` does not) and fails with **2 reads in 0.4 s** on the old code. Two wall-clock users are left on purpose — `progress.py`'s job TTL and `session.py`'s `last_seen` — where the record is an instant with a TTL of minutes or hours and a jump is noise.

- **The MMS polling period has no floor, and what keeps it from flooding the link is the shape of the loop, not a number.** `MIN_INTERVAL = 0.100` is gone from `transport/mms.py`, and so is the clamp `GlvDiagram.set_interval_ms` did against it: `/period` now applies what was asked, cut only at 0 (a negative period is a negative `sleep` later on), and the field in the header is `min="0"`. The guard that replaces it was already there — `effective_interval(requested, last_cycle)` never returns less than the previous cycle cost, and the cycle *includes the relay's answer*, because the loop is synchronous and reads **once** per turn (one batched `read_refs` for the whole page). So the next request never leaves before the previous one came back: at most one read in flight per link, and at most one per RTT no matter how fast the period asks — 0 ms means "as fast as this relay answers" (5.8 ms on the 751's scattered 80-bit page, 435 ms for a whole 1422-bit map), not "as fast as Python can send". `tests/test_mms_transport.py` pins exactly that: a fake relay with a 20 ms RTT polled at 0 ms never has two reads in flight and never exceeds `elapsed / rtt + 1` reads. The one minimum left is `IDLE_INTERVAL` (50 ms), and it is **not** a communications period: it paces the turn that did **not** talk to the relay — an open page with no mapped bit, or an exception that returns instantly — which at period 0 would be a hot loop burning a core without touching the network. That same turn is also kept out of `_record_cycle`, so the "100 ciclos MMS" median stays a measurement of the network and not of an empty loop. Telnet is still **refused** by `/period`, and now for its own reason rather than the floor's: 4xx/7xx Fast Message is several round trips per turn and 3xx is floored at 1.5 s inside its transport (a `TAR <row>` costs ~200 ms *on the relay*), and nobody has bench hardware to measure what tightening those does.

- **Connecting over MMS costs one directory sweep of every LD, and it is seconds, not milliseconds.** Measured: **22 025 names across 5 LDs on the 451-5** (12 735 in ANN alone) and 19 246 on the 751, ~9.4 s of a 10.3 s connect. That is the price of recovering the FC from the relay instead of parsing SCL type templates, and it is well inside the 60 s `glv_setup_timeout` that `setup_done` fences it with — but it is why an MMS diagram takes ten seconds to come up while a warm telnet 4xx takes two. Do not put it on the poll path.
- **A shipped `selfiles`'s packaged `mms_map/` table is the FACTORY default, and on the 487E it is mostly wrong for a configured relay.** Measured on a live SEL-487E-3 R323 (`QPC1_TR1_UPC1`): of 398 drawn bits, 271 are in the shipped table, but the relay's own directory confirms only **58** — the table asks for `IT01PTOC1$ST$Str$general` while the relay publishes `IT1PTOC46`, `IT11PTOC1`, `IT10PTOC55`. Two mismatches at once: the instance is **not zero-padded**, and the PTOC instance numbers are assigned by the relay's configuration, not by the ICD. So MMS coverage came to **54/398 (14 %)** from the table alone and **260/398 (65 %)** with the project SCD attached — which is the ~67 % `fixtures/gle_sem_61850.txt` predicts for this relay, and a reminder that its `cob` column is the union of **SCD ∪ ICD** and never the table by itself. Nothing here is a code fault: `resolve_map` refused every name the relay does not serve, which is the honest half of the design working. But it is why **"SCD do projeto primeiro" is not a preference on a 4xx differential — it is the difference between a usable diagram and a mostly blank one**, and why a 487E without an SCD should be expected to look empty rather than broken. The 451's table, by contrast, matched its relay (166/235, 71 %).
- **Two speed-ups are already measured and rejected.** Pipelining is 3× slower (delayed-ACK) despite `maxServOutstanding=3`; `TCP_NODELAY` changes nothing. Do not retry either without new evidence. The third one, the multi-variable Read, is no longer a plan — it is what the poll loop does (see the batched-read gotcha above).
- **61850 does not expose the whole Relay Word, and on the 7xx it exposes more than telnet.** SEL publishes SELOGIC *state* (`PLT`/`ALT`/`PSV`/`ASV`) and all I/O at 100 %, and no SELOGIC block *output* (`Q`/`R` suffix). But a 751's Fast Meter DNA carries 1116 digitals and zero `VB`, while its 61850 map has 1903 including all 256 `VB` — so the GOOSE pages only work over MMS. Coverage per model is in `fixtures/gle_sem_61850.txt`; regenerate with `tools/gle_vs_61850.py`.
- **An MMS point is only a bit when its leaf DA is a boolean status.** `MmsPoint` carries a `leaf` (`("stVal",)`, `("general",)`, …) and the decoder walks the container's structure positionally at every level. It used to read `stVal` and nothing else, while `resolve_map` mapped any DA the relay's directory confirmed — measured on the tracked corpus (`samples/LT2_UPC1_R1e_GL1.gle.xml` + `samples/substation_demo.scd`, IED `QPC1_LT2_UPC1`, a real 411L): of 222 drawn bits with an `sAddr`, 175 are `stVal`, **43 are `general`** (ACD/ACT — `TRIP` itself is `…$Op$general`, on five pages) and 4 are `instMag.f`. So the badge promised 35/48 on `SCADA_1` for a page that could show 18. The allowlist lives once, in `selfiles.scl.mms_tables` (`BOOLEAN_STATUS_DAS` / `is_boolean_status`), and applies to **both** map sources: a float, a counter (`actVal`), a setting (`setVal`/`setTm`), a quality bitstring (`q`) or a command (`Oper.ctlVal`) is dropped from the map, because `int(bool(x))` of any of those is not a bit reading. Three things depended on that being honest — the coverage badge, `state.error` (which sat permanently at `"leitura parcial: N/M"`, painted red as `ERRO:`, making a real failure indistinguishable from normal), and the two refusals that exist to stop a diagram coming up **LIVE and blank**.
- **One 61850 point can carry TWO Relay Word bits, and `bool("00")` is True.** SEL writes a breaker's position as a single DPS whose Dbpos encodes both auxiliary contacts: `sAddr="db:52A|52B?0:1:2:3"` on `BKR1CSWI1$ST$Pos$stVal`. The alternatives are indexed by the bit combination, **first name = MSB** — (0,0)→0 intermediate, (0,1)→1 open, (1,0)→2 closed, (1,1)→3 bad-state, i.e. exactly Dbpos; the same reading covers `52A?1:2` (one aux contact) and `RELAY_EN?5:1` (a `Mod$stVal`). Measured across the corpus (project SCD + all 345 factory ICDs, 132,250 `db:` addresses): 4.322 single-name and 703 two-name decorations, `len(alternatives) == 2**len(names)` in **5,025 of 5,025**, never more than two names, alternatives always in `{0,1,2,3,5}`. The old key was `sa[3:].upper()`, so the bit's name became the literal string `52A|52B?0:1:2:3` and the whole form vanished silently — 55 of 7,524 drawn bits across the substation's 25 relays, every one of them `52A`, `89CL*` or `89OPN*`. Three things are load-bearing. **(a)** The grammar lives once, in `mms_tables.parse_saddr`, and a shape breaking the invariant is **refused, never guessed** — guessing here is a breaker painted closed while open. **(b)** `py61850` decodes a Dbpos BIT-STRING to the **string** `"10"`, and `bool("00")` is True, so `int(bool(...))` would paint every breaker permanently closed: a point with a rule goes through `mms_tables.decode_bit`, and a value matching no alternative (a real Dbpos=3 against a `?1:2` point) drops the bit from the payload, indeterminate. **(c)** `stVal` alone cannot tell an SPS from a DPS, so the gate is the **DO** (`ENUM_STATUS_DOS`): a `Pos$stVal` without a rule is refused outright, which no plain address in the corpus needs today (0 of 127,225) and which is what stops the fabrication tomorrow. Both bits of a pair share one item, so the read plan de-duplicates the leaf — a pair costs one name in the batch, not two.
- **The two halves of a `selfiles`'s packaged `mms_map/` table come from two sources, and only one is reachable from this repo.** `wordbits.json` — where the plain rows come from — is built by *another* project (`61850Stack/commissioning-app`), whose own `sAddr` walk drops the decorated form too, so fixing this repo's parser does not reach it. `tools/mms_tables_from_wordbits.py` therefore reads the decorated half **straight out of the ICD each model entry's own `path` names**, which is the same file the plain rows came from — no revision is ever mixed, and `wordbits.json` is never rewritten. A decorated row is `[ld_suffix, item, [alternatives, index, nbits]]`; the third element is optional so already-published two-element rows keep loading, and a plain row always wins over a decorated one for the same bit. The FC has to be baked into a table (there is no relay to ask), so it is resolved from that ICD's own `DataTypeTemplates` via `scd.sel_da_fcs` rather than hardcoded — measured, all 2,030 decorated addresses across the 146 corpus ICDs are `ST`, and resolving anyway is what makes a future ICD that disagrees fail loudly instead of shipping an item the relay does not serve. Regeneration added **289 rows across 9 of the 10 tables and changed 0 existing ones**.
- **The SCD gives the same bit two addresses, and the status one has to win.** SEL writes one `sAddr` on both sides of a DO, and the `CO` side usually comes first in document order — `bits.setdefault(...)` therefore picked the command. Measured: 87 points of `QPC1_LT2_UPC1`, `LOCSTA` and `IPRST` among them. `fc_rank` cannot rescue it (it chooses between FCs of one DA, and by then the `stVal` candidate is gone), so `sel_short_addresses` ranks candidates with `mms_tables.da_rank` — boolean status, then anything else, then `Oper.*` — and document order only breaks a tie.
- **`RelayLink` has two locks, and which one a relay conversation holds is the whole point.** `_lock` is lifecycle (transport, poll thread, stop event, `_closed`) and is only ever held for short operations; `_discovery_lock` serialises bit discovery and is the one that stays held for a cold-3xx `TAR` sweep (~90 s) or an MMS layout fetch. While `prepare_bits` held `_lock` across the whole `transport.prepare_bits(...)`, `POST /disconnect` → `pool.release` → `link.close()` blocked behind it and Desconectar looked dead. Splitting them makes the `pause_polling` restart race real, so `_closed` (set by `close()`, checked by `_start_polling`) and `close()` calling `transport.abort()` are part of the same change and cannot be separated from it.
- **A poll loop that returns on its own must take the screen with it.** The three telnet loops set `state.error` and keep looping; the MMS one returns on `Iec61850Error`, because a dropped association does not come back by itself. `RelayLink._poll_runner` is what notices a loop that ended with `stop` unset: it marks the link not-connected and `state.clear()`s, keeping the reason. Without it the tab stayed LIVE with "Desconectar" and `state.digitals` stayed frozen at the last reading, with the SVG still painting those colours under a red badge — the closest this toolkit gets to showing a value nobody read. Two things had to follow it. **(a)** The give-up must never *wait* on `_lock`: `_stop_polling` joins the very thread that is running it while holding that lock, so a blocking acquire turned a close() racing an association drop into a 4.00 s stall — the whole `POLL_JOIN_TIMEOUT`, logged as a wedged reader. It takes the lock with a 0.25 s timeout and walks away, losing nothing: whoever holds it is either closing the link or has already swapped the stop event, which are exactly the two guards that would have sent it home anyway. **(b)** The give-up has to reach the *tab*: it sets `RelayLink._connected`, but `GlvDiagram` answered `self.link is not None`, so the tab still read LIVE. `connected` now means "there is a link AND it is still reading" — and because that alone would leave Conectar as a dead button (`connect_async` returned early on a non-None link), the same change has `connect_async` release a link that gave up before reconnecting. The two halves cannot ship apart.
- **Only the MMS mode overrides `[tcp] port`.** `DEFAULT_PORTS.get(scan_mode, defaults.port)` returned 23 for `"telnet"` and silently overrode a terminal-server or port-forward port, while an *unknown* mode fell through and honoured it. It is `DEFAULT_PORTS[SCAN_MMS] if scan_mode == SCAN_MMS else defaults.port` at both call sites now. **Verified live** through a port-forward: with `[tcp] port = 2001`, a telnet diagram opens and connects at `127.0.0.1:2001` (reaching a real 751 behind it), while an MMS diagram on the same config opens at `203.0.113.41:102`.
- **`selfiles`'s packaged `mms_map/` is the third per-model registry**, after `selfiles`'s packaged `relay_models/` and `selfiles`'s packaged `wordbits/`. Same drift risk, same rule: `tests/test_relay_models.py` fails on an orphan unless it is written down.
- **`corrections_plan.md`, the specs under `docs/superpowers/specs/` dated before 2026-09-01, and the ten `mockups/` predate the PAC CT rename** and still say `sellib` and "Comissionamento SEL". They are a record of what was done, not documentation of what is: they are deliberately not rewritten.

- **`VERSION` names the release being PREPARED; the build adds the `.dev`.** `VERSION` is `1.4.0`, never `1.4.0.dev0` — the dev marker belongs to the build, where the sha is known. `version.build_version()` stamps `1.4.0.dev0+g<sha>` into the bundle's own `VERSION`, so an installed snapshot reports the commit it came from rather than the release it was heading towards. A `VERSION` that already said `.dev0` would make `--release` unbuildable and every snapshot read `.dev0.dev0`. The spelling is the PEP 440 one on purpose: `1.4.0-dev+g<sha>` (as `docs/MIGRATION.md` §5.1 wrote it) and `1.4.0.dev0+g<sha>` are the *same version* under normalisation, and the second is what pip and `importlib.metadata` report back — writing the first guarantees the bundle and the installed package disagree on screen. `version.py` deliberately imports nothing from `pacct`: `tools/build_dist.py` loads it straight from its path, because a build must not need the application's runtime dependencies installed. **MAJOR is reserved for a change to what gets written into a relay** — the `SET_D` round-trip contract, the RDB write path, a settings format — or for dropping a tool or a relay family.

- **`pip install --no-index` does not disable a direct reference, and that broke the offline install silently.** `requirements.txt` pins `cfbwrite` and `selfiles` as `name @ git+https://…@<sha>` because neither is on PyPI (`cfbwrite>=1.0` resolves to nothing — CI was red on it from the day Phase 4 landed, and `app.py` turns a pip failure into "not one of the nine tools comes up"). But `--no-index --find-links vendor/` only switches off the *index*: pip still goes to git for a direct reference, and a substation has neither a network nor, usually, git. It **passed on the build machine anyway**, because pip had the wheel it had just built sitting in its own HTTP cache — exactly the kind of pass that means nothing. So `build_dist.pin_direct_references()` rewrites the BUNDLE's `requirements.txt` to `cfbwrite==1.0.0`, the version of the wheel actually in `vendor/`, and refuses to build when a direct reference has no wheel. The repository's own `requirements.txt` keeps the git pin — that is what a clone, CI and `pip download` need. Verified with `PIP_NO_CACHE_DIR=1`: zero network reads. Both lines become a plain `>=1.0` the day the libraries are published.

- **The `config.ini.example` belongs to the VERSION, `config.ini` to `userdata/`.** `EXAMPLE_CONFIG_FILE` was `DATA_ROOT / "config" / "config.ini.example"`, which is the same directory as `config.ini` — true in a clone, where `PROJECT_ROOT == DATA_ROOT`, and false the moment a versioned install separates them. Measured on a real bundle installed into `PAC-CT/versions/<v>/`: `userdata/config/` holds `config.ini` and nothing else, so `ensure_config_file` found no model, raised `Nao ha modelo para copiar`, and **the dashboard died before opening the port** — an install that completes and then cannot start. It is `PROJECT_ROOT / "config" / "config.ini.example"` now, which is also the marker `_find_project_root` looks for. Anything else that ships with the code and is read through `DATA_ROOT` has the same bug waiting.

- **The updater's five rules, and none of them is taste.** (1) **Never on the boot path** — a check is `--atualizar`, same rule and same reason as `install_requirements` only running pip when an import fails; offline is a printed sentence, not a traceback. (2) **Verify before unpacking** — the sha256 comes from the release's own `manifest.json` and a missing entry is *refused*, because "no sha to check" and "sha matches" must never take the same branch. (3) **Stage, then swap, then restart** — the new version is unpacked and given its venv beside the running one, and only then is `current` repointed; a running process cannot reliably replace its own loaded extension modules on Windows, which is what makes the versioned layout safe rather than merely tidy. (4) **Only releases** — a `1.4.0.dev0+g<sha>` snapshot is never offered, because the commit it names may never become one. (5) **`userdata/` is never read, moved or migrated.** `unpack()` also refuses an archive that is not exactly one top-level directory, and any member that would climb out of the destination — it is a file fetched over the internet and extracted with the caller's rights. `Layout.detect()` returning `None` for a git checkout is what stops `--atualizar` swapping a development clone under its own feet.

- **A `v*` tag is checked against `VERSION` before anything is built.** A release whose contents do not match its number is the one artefact this project must never produce: it is what the updater trusts, sight unseen, on a machine in a substation. The `pre-push` hook builds `--no-vendor` (seconds, no network — the wheels are not what breaks; `PACCT_PREPUSH_VENDOR=1` asks for the full one), and CI runs the same source-only build as a step, because hooks are not versioned and a machine that never ran `tools/install_hooks.sh` must still not be able to cut a release whose bundle does not build.

- **The Windows half of the distribution has never been run.** `mklink /J` for the `current` junction (a junction, not a symlink: it needs no administrator rights), `pac-ct.cmd`, and a venv built from `win_amd64` wheels are written against the documented behaviour and reviewed, but there is no Windows machine here. It needs one pass on Windows before 1.4.0 is tagged. Everything else in Phase 5 was verified end to end on Linux: a real bundle built, installed offline with pip's cache disabled, all eleven screens served from it, and `current` swapped and rolled back under a running launcher with `userdata/` byte-identical throughout.
