# py61850 — what an MMS polling client needs (4 findings, 1 blocker)

*Draft issue for github.com/GuilhermeMarini/py61850 — 2026-08-29*

## Context

Building live polling on top of `MmsClient` for a substation commissioning tool:
read N Relay Word bits off a SEL relay every ~100 ms and paint them onto a logic
diagram. The library does this correctly today; the four items below are what
stop it doing it *efficiently*, and the first one is a silent-failure bug.

**Environment.** py61850 `0.2.0.dev0` (2e8474d), Python 3.12, against a live
**SEL-451-5, FID `SEL-451-5-R331-V1-Z033014-D20250919`**. Every number below is
measured on that relay, not estimated.

**What the fixes are worth.** Reading 170 bits (a real logic diagram) currently
costs 170 requests / 739 ms. Grouped per `LN$FC` container it is 30 requests /
187 ms. With a working multi-variable Read it is **12 requests / 81 ms and a
third less traffic** — but that path is unreachable because of #1.

---

## 1. `CotpTransport.send()` never fragments — requests over 1024 B silently kill the association

**Severity: blocker.** This is the item that matters; the rest are ergonomics.

`send()` always emits a single DT TPDU with the EOT bit set, whatever the payload
size:

```python
# src/py61850/osi/cotp.py
def send(self, data: bytes):
    """Send an upper-layer payload as a COTP DT TPDU (EOT set)."""
    self._send_tpkt(bytes([0x02, DT, 0x80]) + data)
```

…while `connect()` negotiates `tpdu_size=0x0a` (1024 bytes) in the CR. `recv()`
*does* reassemble incoming DT fragments, so the transport is asymmetric: it can
receive a fragmented stream but never produces one.

Consequence: any request whose wire form exceeds the negotiated TPDU size makes
the relay close the connection. There is no MMS error and no service reject —
the next `recv()` raises `TransportError: connection closed by peer`, which
reads like a network fault rather than a protocol violation by the client.

**Measured threshold**, growing a multi-variable Read one item at a time:

| items | request on the wire | result |
|---|---|---|
| 16 | 838 B | OK, 16 values |
| 18 | 938 B | OK, 18 values |
| 20 | 1038 B | **association dropped** |
| 24 | 1238 B | **association dropped** |

Raising the *proposed* `tpdu_size` to `0x0c` (4096) does not help — the relay
negotiates back down to 1024 in the CC, and `connect()` never reads that value
(see #2), so nothing in the client knows.

**Proposed fix.** Fragment in `send()`: split the payload into
`negotiated_tpdu_size - 3` chunks, EOT clear (`0x00`) on every fragment but the
last, EOT set (`0x80`) on the last. Mirror of what `recv()` already reassembles.

**Acceptance.** A Read carrying 64 variables (~3.2 kB) completes over a
1024-byte-negotiated link and returns 64 values.

## 2. The negotiated limits are parsed by nobody, so no caller can size a request

Two separate places discard the numbers a client needs:

- `CotpTransport.connect()` checks the CC is a CC and returns it, but never
  parses the TPDU-size parameter the peer answered with. `self.tpdu_size` keeps
  holding what *we proposed*, which after negotiation may be a lie.
- `MmsClientBase.connect()` checks the Initiate-Response tag and throws the rest
  away. That PDU carries `localDetailCalled` and the `maxServOutstanding` pair.

Decoded by hand on the 451, the relay answers:

```python
{'localDetailCalled': 12000,
 'maxServOutstandingCalling': 3,
 'maxServOutstandingCalled': 3}
```

Note 12000 is the *MMS* PDU ceiling while the *COTP* ceiling is 1024 — they are
different limits and a batching client has to respect the smaller.

**Proposed fix.** Parse both and expose them read-only:
`CotpTransport.negotiated_tpdu_size`, and on the client
`max_pdu_size` / `max_outstanding`. Cheap, and it turns "how many variables may
I ask for?" from guesswork into arithmetic.

## 3. `Read` supports exactly one variable, and DataSets cannot be read or listed

`build_read` hardcodes a single entry:

```python
# src/py61850/mms/pdu.py
def build_read(domain: str, item: str) -> bytes:
    var = ber.tlv(0xA0, object_name(domain, item))
    list_of_var = ber.tlv(0x30, var)
    spec = ber.tlv(0xA1, ber.tlv(0xA0, list_of_var))
    return ber.tlv(SVC_READ, spec)
```

`listOfVariable` is `[0] IMPLICIT SEQUENCE OF SEQUENCE { variableSpecification,
alternateAccess OPTIONAL }`, so N entries means N repetitions of the inner
`0x30` — not one `0x30` holding N names. (I got this wrong first: the relay
accepted the malformed PDU and returned **one** value, which is a quietly
misleading way to fail.)

Verified working against the 451:

```python
def build_read_multi(domain, items):
    entries = b"".join(
        ber.tlv(0x30, ber.tlv(0xA0, object_name(domain, it))) for it in items)
    return ber.tlv(SVC_READ, ber.tlv(0xA1, ber.tlv(0xA0, entries)))
```

`decode_read_response` already handles the N-result case with no change — it
returned 2, 8 and 18 values correctly. Above 18 it hits #1.

Also missing on the same service group:

- **`variableListName` form.** `VariableAccessSpecification` also allows
  `variableListName [1] ObjectName`, i.e. read a whole named DataSet in one
  request. SEL ICDs ship predefined sets (`BRDSet01`…) that map neatly onto what
  a client wants to poll.
- **`get_logical_device_directory` has no `object_class` parameter**, so DataSets
  cannot be enumerated at all — `GetNameList` with `objectClass=namedVariableList`
  is unreachable from the public API.

**Proposed fix.** `read_many(domain, items)` (chunked internally against the
negotiated limits from #2), a `variableListName` form, and an `object_class`
argument on the directory call.

## 4. `TCP_NODELAY` is never set — measured as harmless here, but it should be a decision

`grep -rn "NODELAY\|setsockopt" src/py61850/` returns nothing. For a
request/response protocol on small PDUs, Nagle is the classic latency trap, so
this looks like a bug even though it measured as not being one:

| | single read | 8-container cycle |
|---|---|---|
| `TCP_NODELAY=0` | 9.06 ms | 104.4 ms |
| `TCP_NODELAY=1` | 8.85 ms | 99.4 ms |

(Same socket, option flipped, taken during a busy period — the relay's quiet-time
median is 3.1 ms.) No meaningful difference, so this is low priority. Worth
setting explicitly anyway, with a comment recording that it was measured, so the
next person doesn't spend an afternoon on it.

---

## Negative result worth recording: do not add pipelining

The relay advertises `maxServOutstanding=3`, so I tried writing 3 requests
before reading any response. It is **3× slower**:

| reads | sequential | pipelined (depth 3) |
|---|---|---|
| 3 | 14.5 ms | 52.1 ms |
| 6 | 28.4 ms | 91.8 ms |
| 8 | 37.0 ms | 68.0 ms |

The ~+40 ms is the delayed-ACK signature. Batching into one PDU (#3) is the
right lever; concurrency on the socket is not. Suggest capturing this in the
ROADMAP so it does not get proposed again.
